# SmartCrate Sensor Integration

This directory contains a documented ESP32 example and a local simulator for the existing backend sensor-ingestion endpoint.

## Hardware assumptions

- ESP32 or ESP32-S3 with Wi-Fi
- DHT22-class temperature/humidity sensor
- VOC/gas sensor, or a separately calibrated ethylene sensor
- Optional CO2 sensor
- Optional scale/current-weight source

The firmware keeps sensor reads behind `readTemperature()`, `readHumidity()`, `readVoc()`, `readEthylene()`, `readCo2()`, and `readCurrentWeight()`. Replace the placeholder implementations with the actual libraries and wiring for the selected hardware.

MQ-series sensors must not be labeled as calibrated ethylene ppm without a real calibration procedure. An uncalibrated MQ output should be sent as `voc`/gas index or raw sensor data, not as `ethylene`.

## Payload contract

`POST /api/sensors/readings`

```json
{
  "deviceId": "SC-ESP32-001",
  "harvestId": "<real-harvest-id>",
  "temperature": 25.5,
  "humidity": 61.2,
  "voc": 0.82,
  "ethylene": null,
  "co2": null,
  "currentWeight": 95.0,
  "observedAt": "2026-09-25T09:30:00.000Z"
}
```

Field meanings:

- `temperature`: degrees Celsius
- `humidity`: relative humidity percentage
- `voc`: VOC/gas index
- `ethylene`: calibrated ethylene ppm only when a calibrated ethylene sensor is used
- `co2`: ppm
- `currentWeight`: kilograms
- `observedAt`: ISO-8601 timestamp generated by the device clock
- `deviceId`: registered device identifier
- `harvestId`: real backend harvest identifier

Temperature and humidity are required. Gas, ethylene, CO2, and weight fields are optional.

## Device authentication

Hardware sends its secret in the `X-Device-Api-Key` header. The backend stores only a SHA-256 hash in `Device.apiKeyHash`; the raw key belongs on the device and must not be committed to source control or exposed to React.

A device is authorized for a harvest when its registered `farmerId` matches the harvest's `farmerId`. Create a device record through a controlled administrative/database process, for example:

```js
const crypto = require('crypto');
crypto.createHash('sha256').update(process.env.DEVICE_API_KEY).digest('hex');
```

Store the resulting hash in a `Device` record with `deviceId`, `farmerId`, and `isActive: true`. Do not put the raw key in the database.

## ESP32 flow

1. Connect to Wi-Fi.
2. Synchronize time with NTP.
3. Read sensor values through the modular sensor functions.
4. Build the payload above.
5. Send the device API key in `X-Device-Api-Key`.
6. POST to the backend.
7. Treat 2xx as accepted.
8. Back off after network/5xx failures.
9. Do not retry the same `deviceId + observedAt` indefinitely; the backend deduplicates that pair.
10. Never send `hours_since_harvest`, prediction values, or farmer IDs.

The backend stores the reading and triggers the existing prediction workflow. The firmware does not call FastAPI directly.

## Local simulated-device flow

The simulator uses the same endpoint and payload shape but authenticates with the existing farmer JWT and adds `source: "simulator"`. It is explicitly development-only and does not represent physical hardware.

From the repository root, after obtaining a valid JWT and harvest ID:

```powershell
$env:SMARTCRATE_API_URL = "http://localhost:5000/api"
$env:SMARTCRATE_JWT = "<farmer-jwt>"
node hardware/simulate_sensor_reading.js <harvest-id>
```

The simulator submits sensor readings only. Node.js and the existing ML service calculate the prediction; the simulator never sends risk or shelf-life values.

## Tinkercad limitation

Tinkercad does not provide a direct ESP32-to-React live integration path. An Arduino Uno plus DHT sensor and potentiometer/MQ-style circuit can demonstrate sensor behavior, but those values remain a hardware simulation. They must enter SmartCrate through the same backend API contract. React still communicates only with Node.js.

## Validation and troubleshooting

- `401`: missing/invalid device API key, or simulator missing farmer JWT
- `403`: device/farmer does not own the target harvest
- `400`: invalid or future `observedAt`, invalid harvest timestamp, or incompatible range
- `422`: request schema validation failed
- `200` with `duplicate: true`: same hardware `deviceId + observedAt` was already stored
- `201`: new sensor reading stored; prediction processing was triggered asynchronously
- If ethylene is unavailable, omit it. Do not send an MQ reading as calibrated ethylene.
- If the ML service is unavailable, the backend preserves its explicitly labeled rule-based fallback behavior.
- Physical hardware was not tested as part of this phase.
